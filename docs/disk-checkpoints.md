# Disk-backed checkpoints with capnp-zig — options

Status: exploration (2026-10-09). Nothing here is built. The user asked for
this to be considered with capnp-zig (`/Users/nullstyle/prj/zig/capnp-zig`,
v0.25.0) as the serialization layer.

## 1. Why

Today checkpoints live in memory only: at most `max_checkpoints` document
copies, kept near the marker, and gone when the process ends. Two things
follow:

- Reopening a document replays everything. At 100k features that is tens
  of milliseconds for the first `state()`; a mid-history edit later replays
  from the seed, because only the last few intervals keep a checkpoint
  (the parked "checkpoint spread" item).
- Memory pressure can only drop checkpoints (`trim`), never move them.

A store on disk fixes both: evicted checkpoints are spilled instead of
destroyed, and a reopened document warms its cache from the store.

## 2. What exists to build on

- `Domain.encodeDoc` / `decodeDoc`: the document codecs persistence already
  uses for the seed.
- `Checkpoints` (src/checkpoint.zig): the in-memory cache with eviction,
  pins, `bestBefore`, statuses per entry.
- `prefixVersion(pos)` and the change list: exact in-session knowledge of
  whether `features[0..pos)` changed.
- FTZ7 containers: id, format version, order and edit keys.
- capnp-zig core: `MessageBuilder` / `StructBuilder` / `StructReader`,
  plain and packed encodings, message validation on read, zero-copy reads.

## 3. The questions that parked this

| Question | Answer proposed here |
|---|---|
| Who owns the files | The app, through a store it opens (`Io.Dir`); the library never picks a path. |
| How a checkpoint stays valid across edits and sessions | A checkpoint is keyed by `(timeline_id, pos, prefix digest)`. The prefix digest hashes `features[0..pos)` (ids, order keys, edit keys, suppression) and the parameters. In session, the change list drops invalid ones as today; across sessions, a checkpoint whose digest no longer matches the loaded prefix is ignored. |
| A half-written file on crash | Write to a temporary name, then rename over the final name. On read, capnp validation (or a length plus checksum frame) rejects a torn file; it is deleted. |
| Documents that read other timelines | Their checkpoints depend on the other timelines' state too. First version: a timeline with a `links` hook does not spill (its window stays in memory). Later: record each linked timeline's digest in the key. |

## 4. The store, independent of the format

```zig
pub const CheckpointKey = struct { timeline: u64, pos: u32, prefix: u64 };

/// What the library needs from a store; the app provides it.
pub const CheckpointStore = struct {
    ctx: *anyopaque,
    put: *const fn (ctx: *anyopaque, key: CheckpointKey, bytes: []const u8) anyerror!void,
    get: *const fn (ctx: *anyopaque, key: CheckpointKey, gpa: Allocator) anyerror!?[]u8,
    list: *const fn (ctx: *anyopaque, timeline: u64, gpa: Allocator) anyerror![]CheckpointKey,
    drop: *const fn (ctx: *anyopaque, key: CheckpointKey) void,
};

Config.checkpoint_store: ?CheckpointStore = null,
```

- The library ships `ft.disk.DirStore`: one file per checkpoint under
  `<dir>/<timeline id hex>/<pos>-<prefix hex>.ckpt`, temp-and-rename writes,
  bounded by a byte budget with oldest-first eviction.
- Eviction in `Checkpoints` spills instead of destroying when a store is
  set; `bestBefore` falls back to the store's nearest valid checkpoint at or
  before the position; `persistence.load` with a store warms the cache with
  whatever is valid. `trim` can spill everything.
- A spilled checkpoint carries the statuses too, so a marker that lands
  exactly on it restores them, as the in-memory one does.

Side effect: every interval checkpoint that the window would evict is kept
on disk, so a mid-history edit replays from the nearest disk checkpoint. That
is the "checkpoint spread" item, delivered by the same mechanism.

## 5. Three ways to write the file

### A. capnp with generated code

A schema `schema/checkpoint.capnp`:

```capnp
struct Checkpoint {
  timelineId   @0 :UInt64;
  pos          @1 :UInt32;
  prefixDigest @2 :UInt64;
  formatVersion @3 :UInt32;     # the Domain's, for migrateDoc
  doc          @4 :Data;        # Domain.encodeDoc bytes
  statuses     @5 :List(Status);
  struct Status { kind @0 :UInt8; message @1 :Text; }
}
```

The plugin generates `Checkpoint.Builder` / `Checkpoint.Reader`. Cost: the
code generator needs the pinned WASM Cap'n Proto compiler and Wasmtime 48.0.1
(capnp-zig's own toolchain pin), or the generated `.zig` is committed and
regenerated by hand at each capnp-zig bump. Full schema tooling, evolution
and validation.

### B. capnp without generated code

The same layout, written by hand with the generic API: one
`allocateStruct(3 data words, 2 pointer words)`, `writeU64` / `writeU32`,
`setData` for the document, `initStructList` for the statuses; read with
`Message.init` (validated) and `StructReader.readU64` / `readData` /
`readStructList`. The schema file is checked in as the documentation of the
layout, so A can replace B later with byte-identical files. No compiler, no
Wasmtime, one dependency fetched from a tag. Validation, packed encoding and
field-at-the-end evolution still apply.

### C. Our own framing

The FTZ style: magic, length-framed fields, a checksum. No new dependency
and no schema tooling. Listed for completeness.

| | A codegen | B hand-built | C own framing |
|---|---|---|---|
| New dependency | capnp-zig + compiler toolchain | capnp-zig core | none |
| CI | Wasmtime pin or committed generated code | nothing new | nothing new |
| Validation on read | yes | yes | checksum only |
| Schema evolution | yes | by convention (append fields) | by version byte |
| Code to write | small | small (~120 lines of layout) | small |
| Risk | toolchain drift between generator and runtime | layout typos (one struct, testable) | none |

## 6. Recommendation

Build the store and the timeline integration (section 4) with **B** for
the file format, and check the schema file in next to the hand layout. It
gives capnp-zig a real consumer today without the compiler in CI; **A** can
take over byte-for-byte when the toolchain is convenient. Keep **C** out.

Then, as follow-ups: let the geo editor use the store (`save` spills, `load`
warms: reopen without replay); consider the same path for the FTZ container
itself, which is where schema evolution pays most.

Decisions to confirm: B now (A later), the prefix digest as the validity
key, one file per checkpoint, and no spilling for linked documents in the
first version.
